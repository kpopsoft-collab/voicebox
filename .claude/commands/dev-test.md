# 🛠️ dev-test: Merge Readiness & Quality Gate

개발 작업을 마친 직후 코드의 품질과 안정성을 검증하고, P0/P1 결함을 즉시 수정한 뒤 머지 가능 여부를 최종 판정합니다.

---

## 📋 파라미터 및 대상 범위

- **기본 실행 (`/dev-test`)**: 워킹 트리의 스테이징 + 미스테이징 변경사항 (`git diff HEAD`)
- **인자 지정 (예: `/dev-test main`, `/dev-test HEAD~2`)**: 지정한 base ref와 현재 브랜치 간의 diff

---

## 🔄 실행 단계 (Execution Pipeline)

### Step 1: 컨텍스트 수집 및 쉘 스크립트 실행
1. 아래 검증 스크립트를 우선 실행하여 diff 및 1차 테스트 상태를 확인합니다:
   ```bash
   ./scripts/dev-test.sh $ARGUMENTS
   ```
2. diff가 비어 있으면 **"변경 사항 없음"**을 출력하고 즉시 종료합니다.
3. diff 내용을 분석하여 이번 변경의 **핵심 의도를 2~3문장으로 명확히 요약**합니다.

---

### Step 2: 엄격한 심각도별 코드 리뷰
다음 항목을 순서대로 점검합니다:
**정확성(Logic) → 보안 → 에러 처리 → 엣지 케이스 → 성능 → 가독성 → 테스트 가능성**

| 심각도 | 정의 | 조치 기준 |
| :--- | :--- | :--- |
| **P0 (Critical)** | 데이터 손실, 보안 취약점, 서비스 다운/크래시, 머지 차단 사유 | 즉시 수정 & 사람이 반드시 최종 재확인 |
| **P1 (High)** | 특정 조건에서 확실한 오동작, 메모리/리소스 누수, 타입/런타임 에러 | 이번 단계에서 즉시 자동 수정 |
| **P2 (Medium)** | 가독성 저하, 경미한 비효율, 향후 기술 부채 | 리포트에 기록만 남김 (코드 수정 X) |
| **P3 (Low)** | 사소한 코드 스타일, 띄어쓰기, 주석 선호도 | 리포트에 언급하지 않음 |

---

### Step 3: P0 / P1 결함 수정 (최소 변경 원칙)
- **P0 및 P1 항목만** Edit으로 수정합니다.
- **수정 규칙**:
  - 공개 API 시그니처나 인터페이스를 임의로 변경하지 않습니다.
  - 새로운 외부 의존성(패키지)을 추가하지 않습니다.
  - 요청받지 않은 대규모 리팩터링이나 단순 포맷팅은 절대 수행하지 않습니다.

---

### Step 4: 프로젝트 테스트 자동 실행 & 자가 수정 루프
1. 프로젝트의 테스트 러너를 실행합니다:
   - `bun run typecheck` / `npm test` / `pytest` / `cargo test` 등
2. 테스트 설정이 없는 경우: `"테스트 러너 미발견"`으로 보고하고 다음 단계로 이동합니다.
3. 테스트 실패 시:
   - 이번 변경으로 인해 발생한 오류인지 원인 분석
   - 코드 수정 후 재실행 (**최대 2회 반복**)
   - ⚠️ **주의**: 테스트를 억지로 통과시키기 위해 기존 `assert` 문을 삭제하거나 완화하는 행위 금지

---

### Step 5: 회귀(Regression) 재검증
- 수정 후 `git diff`를 다시 확인하여 수정한 코드로 인해 새로운 사이드 이펙트나 문제가 발생하지 않았는지 검토합니다.

---

### Step 6: 최종 판정 리포트 출력

반드시 아래 Markdown 템플릿 형태로 최종 결과를 출력합니다:

```markdown
## 📌 변경 요약
(무엇을 왜 변경했는지 2~3문장)

## 🔍 리뷰 결과
| 심각도 | 파일:라인 | 문제 설명 | 조치 사항 |
| :--- | :--- | :--- | :--- |
| P0/P1 | `path/to/file.ext:123` | 문제 요약 | 수정 완료 / 수동 확인 필요 |

## 🛠️ 적용한 수정
- `파일:라인` — 무엇을 왜 수정했는지 1줄 설명

## 🧪 테스트 결과
- **실행 커맨드:** `<실행한 테스트 명령어>`
- **결과:** `<통과 N개 / 실패 N개 / 미실행>`
- **실패 항목 및 조치:** (실패 및 해결 내역이 있을 때만 기재)

## 📝 남은 제안 (P2)
- `파일:라인` — 향후 개선 권장 사항 (1줄씩)

## 🚦 최종 판정
**[ MERGE OK / 수정 필요 / 확인 필요 ]** — <명확한 사유 1줄>
```

---

## ⚠️ 판정 기준 (Verdict Rules)
- **`MERGE OK`**: P0/P1 이슈가 모두 해결되었고, 모든 테스트가 정상 통과함.
- **`수정 필요`**: P0/P1 버그가 남아있거나 테스트가 여전히 실패함.
- **`확인 필요`**: P0 결함이 수정되었으나 사람의 도메인 검증이 필요하거나, 테스트 러너를 발견하지 못한 경우.
